aburan28/crypto

Cryptography, and the cost of breaking it

A from-scratch implementation of the major cryptographic algorithm families in Rust, and a cryptanalysis suite built to answer one question about each attack it implements: where is the crossover, actually? Published here are the cost ledger that answer lives in, a live distinguished-point campaign, and the notes behind both.

Not for production use

The library is an educational reimplementation. It is not constant-time — the big-integer arithmetic branches on secret values, so every RSA, ECDSA, ECDH and ECC operation leaks through timing, and the AES S-box is a lookup table open to cache-timing attacks. It has had no third-party audit, and some parameter sets in it are deliberately far below any security level. SECURITY.md lists the structural limitations in full, with the audited alternatives to use instead.

How a result is reported here

A cryptanalysis thread can run for weeks, improve its own headline number by two orders of magnitude and have established nothing. The convention that prevents it is the one worth knowing before reading anything else on this site: progress is a ratio to a boundary, reported in a single table whose rows are variants and whose columns are one unit.

The unit
S = ops / √n

Group operations per square root of the group order. Every cost the method incurs is inside it: precomputation, table setup, relation verification, linear algebra, and any work an oracle does per call. Picking the unit this way makes rho flat at every size, so “is this better than rho” becomes reading one column.

A floor
κ ≥ √(2(B+1)/γ)

A lower bound from a counting argument rather than a measurement: generic relation yield from P residuals is at most γP²/2n. It moves only with the factor-base size and the automorphism order, so it cannot be tuned away.

A reference
rho, S ≈ 1.3

The cost of the best algorithm that already solves the same problem, measured in the same unit on the same instances: 1.2 to 1.8 across four group sizes. A boundary chosen after the fact is not a boundary, so both are written down before any optimising starts.

Every change then gets classified, and only the first of the four is worth calling a result:

The four classes a measured change can fall into
ClassWhat movedWhat it means
advance ratio to the floor fell the method does something a generic algorithm cannot
engineering S fell, ratio to the floor flat legitimate, bounded, and not a finding
relabelling headline count fell, S rose work moved somewhere the headline does not look
accounting numbers changed, algorithm did not a correction; say so and do not claim the gain

The unit, the floor and the reference figures above are quoted from the scoreboard; the reporting rule itself is in AGENTS.md.

What it costs you: one GPU queue and one worker thread, paused by default as soon as the tab is hidden, and stopped the moment the switch goes off. What it establishes: nothing about a deployed curve. The instances are generated toy curves whose orders are known, so the measurement this produces is a throughput figure — steps per second, and the expected walk length it has to be divided into — not a ratio to any boundary. Before a rate is reported the engine replays its first 32 device steps in BigInt on the host and refuses to run if the device disagrees. Source: rho-gpu.wgsl, rho-gpu-host.js, the note.

Research notes

Each note carries its own boundary, table and falsification target. The bottom lines here are mostly negative results stated in numbers, which is what a finished thread looks like when the answer is no.

  • Residual walks over partial decompositions

    The reference implementation of the reporting rule, end to end. Result in one line: every residual-collision hybrid tested recovers the planted logarithm correctly, and every one of them needs ≈ √(2n(B+1)) residuals to do it — a factor √(2(B+1)) more than plain Pollard rho needs steps. The walk changes how cheaply a residual is constructed, not how many a collision needs.

  • Index calculus on Koblitz curves

    Frobenius-invariant factor bases, Semaev summation polynomials and Gröbner solving, with a scoped scaling target and pre-registered hypotheses in a companion note.

  • Reducing the solving degree

    The offensive side of the first-fall-degree program: whether the Gröbner solving degree is a property of the system or of the presentation chosen for it.

  • A proof-complexity bridge for the first-fall-degree assumption

    Reads the disputed first-fall-degree heuristic as, up to constants, a statement about Polynomial Calculus refutation size.

  • Exotic coordinates for point decomposition

    An algorithmic search for point representations beyond affine, projective and Jacobian that give better relations between points, rather than a trawl through formula databases.

  • secp256k1's j = 0 / disc = −3 CM structure

    Whether the unusual endomorphism ring of secp256k1 leaks anything ECDLP-relevant, with a PARI/GP artefact that reproduces every invariant in the note.

  • ECC2K-130 and ECC2K-95 walk engines

    The CPU, GPU and HDL walk implementations behind the live campaign, and the measured throughput ceiling of each.

  • A visual primer: CM, Jacobian, twist, isogeny, rank, embedding degree

    No prerequisites. The six terms that show up everywhere above, each as what it is, a picture, and what it looks like in secp256k1 — read this first if the notes read as jargon.

What this site does not claim

Nothing published here breaks a deployed curve. The scoreboard's variants are measured against Pollard rho and a generic-group floor precisely so that a cost improvement cannot be mistaken for a break, and the campaign page reports distinguished-point counts for a published challenge curve: a recorded collision there is not a discrete-log recovery until an independent solver has checked [k]P = Q.
