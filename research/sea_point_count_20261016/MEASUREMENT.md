# Measurement contract and accounting

The executable source is in `native/`; algorithm source is frozen at the two
revisions in PROTOCOL.md. The baseline worktree contains only the original
crate plus a byte-for-byte copy of `measure.rs` and its Cargo manifest. The
candidate worker links the changed crate. `evidence/frozen-hashes.txt` pins
both worker binaries, the reservation executable, and the canonical Phi cache.
`evidence/algorithm-diff.txt` is empty: the timed candidate algorithm source
matches revision 44f8d17f. A CM generator correctness fix was made after timing;
it is not part of either timed arm and is not benchmarked here. The replay
script builds both arms in frozen worktrees, including the original candidate.

## Accounting intervals

| Workload | Included inside algorithm timer | Excluded from timer |
| --- | --- | --- |
| bsgs24, bsgs32, bsgs40 | Every `curve::order` call, RNG construction, reference-order assertion and black-box consumption | Process launch, validated curve construction, field conversion, ICV1 calculation and output |
| sea40_cached, sea192_cached | Every `sea::sea` call, fixed seed schedule, order assertion and black-box consumption | Field conversion, canonical cache import, and one warm-up call; `setup_ns` records import/warm-up separately |
| count192_cold | Every `api::count_points` call, including field dispatch, fresh Phi construction, point count, curve/twist certification, and assertion of expected order and both certificates | Process launch and validated input-model construction |
| cm256_control | The same complete-count API interval on secp256k1, through its unchanged CM route | The same input/process exclusions |

Each workload uses one exact registered curve model. The source fixes its
order and repetition count. Seeds follow `1 + i % 4`; a one-call P-192 sample
therefore uses seed 1. This is not a distributional statement about arbitrary
curves or a multi-target DLP workload. The result records carry the ICV1 slug,
order, call count and seed schedule. The native analyzer checks registry
membership and exact paired output/work agreement before calculating ratios.
After timing, it separately calls `api::check_order` for each registered
reference and retains its curve/twist certificates and established divisors.
This check is independent of the point-count search strategy, but shares the
library's field/point arithmetic and probable-prime assumptions. It is not an
independent verified implementation of that arithmetic.

The warm Phi file is bound to the full modulus and stores canonical integer
coefficients. It is deterministically generated by the original implementation,
not copied from an unverified external database. The preparation command,
recorded setup cost and hash are retained. The file can be regenerated using
the replay recipe, so the multi-megabyte setup product is excluded from Git.
Cold count never reads this harness cache.

## Isolation and its limits

`reserve.rs` uses the repository's `/tmp/crypto-bench.lock`, reserves CPU 4,
moves movable visible threads off it, and restores their affinities on exit.
Workers inherit a single-CPU mask and `RAYON_NUM_THREADS=1`. The observer runs
on housekeeping CPUs rather than sharing the benchmark CPU. Before every
sample, the runner checks two seconds of visible other-process CPU use against
0.10 CPU on average. It checks available CPU/memory PSI against 5.0, matching
the repository isolation policy.

This VM does not expose `/proc/pressure`. The host record stores null PSI,
not a successful pressure observation. Some idle system threads owned by a
different user cannot be moved; their ids are retained. Therefore the run is
described as pinned with movable-thread eviction and visible-process monitoring,
not as an exclusive-host or full L2 measurement. Cloud neighbors and CPU
frequency are uncontrolled. A/A quantifies observed repeatability under these
conditions; it cannot prove absence of all external noise.

Per sample, the runner records algorithm nanoseconds, enclosing child wall time,
child user/system CPU, faults and context switches, preflight CPU use, other
visible-process CPU use and timeout/exit status. A sample is marked contended
when visible other-process use exceeds 0.10 CPU on average during it, as in
tools/isolated_bench.py. The native replacement retains that policy; it performs
no Python research orchestration. Before/after process snapshots can miss work
by very short-lived processes, another limit on the isolation claim.

No build, test suite, proof checker, PDF renderer or analysis process is run on
this host during timing. Source/report preparation and brief progress reads
remain on housekeeping CPUs and are subject to the same contention accounting.

## Comparison and interpretation

Five A/A pairs precede five interleaved A/B pairs for each workload. Summary
times are microseconds per counted call. The summary reports each arm's median
and minimum, the median of paired A/B ratios and their minimum/maximum, and
the maximum absolute paired A/A deviation from 1. A ratio above 1 means the
candidate took less time. Pairs with either sample marked contended are retained
but excluded from admitted summaries. Failed, mismatched or incomplete records
are rejected, rather than counted as faster runs.

An A/B effect within that workload's A/A envelope is reported as inconclusive.
This is a conservative descriptive noise comparison with five pairs, not a
confidence interval or a proof of speedup on other hardware. The warm and cold
rows have different included work; a warm-stage gain is not an end-to-end gain.
