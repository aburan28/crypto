# n=53 compact-orbit rank and point-only recovery

Status: **full-rank public-synthetic n=53 log recovery, with a cold cost receipt; no matched-rho or ECC2K-130 performance verdict.** This follows the deterministic relation producer promoted by PR #720. The frozen relation-collection run used that producer unchanged. The follow-up source adds point-only input and repairs batch accounting; its final source SHA-256 is `b88ab958f3044211ddcb230863a4175916000c2c15307a7572dec40a4e55204d` and its release executable SHA-256 is `01ab8d0b09f72908281124ae3ae4fdde88f538abdc1fc2c574309dfc1777990c`.

The factor base is the certified n=53, a=0, order-21,044,858,204,113 base from PR #714: 220 signed-Frobenius orbit columns, 23,320 points, 11,660 x values, and point-set SHA-256 `d859319015ea405fd18aee41b51396ce4edcab64ef66265d8edcdeb5e040eb71`. The committed gzip header in `independent_replay_20260924_codex` is reused, not copied into each run. Target scalars are the first 512 distinct values of the SHA-256 schedule `ECC2K53-COMPACT-COLD-BATCH-20260924-v1/` reduced modulo the subgroup order; the manifest and scalar file were written before the producer ran. Every target is a known-scalar multiple of G. The producer built one regular-state/root index and queried all 512 targets in a single cold process. It accepted 512 relations and reported no failures. A separate Python implementation checked each S3 identity, both pair sums, full group lift and target equation; it also checked every orbit point label by Frobenius and all 220 solved factor-base logs by scalar multiplication. The matrix first reached rank 220 at admitted relation 461; the next 51 relations predicted their held-out scalar labels from that frozen full-rank solution.

The cold training process took **158.127 seconds wall** and peaked at **646,742,016 bytes RSS** on this local host. The producer's old stage subtotal was 154.832 seconds, including 0.597 seconds regular scan, 0.206 seconds root-index build and 153.979 seconds summed extraction queries. That subtotal excluded some curve/setup, target generation and group-validation work. The *old* raw receipt also says `sat_verification_included=true` and adds `solve_ms` again in `charged_total_with_sat_ms`. This is a producer accounting defect: `KIC_ORBIT_BATCH_ONLY=1` never calls SAT; the old `solve_ms` clock encompassed scan/extraction and double counted it. The raw receipt is preserved verbatim. The follow-up source reports `sat_verification_included=false`, null SAT time, a full target-loop subtotal and separate `sat_solver_invocations`/`sat_solver_ms` counters. **Use cold process wall**, rather than either stage subtotal, for this run's inclusive cost.

The follow-up point-only input accepts JSONL `[x,y]` public points, checks curve and prime-subgroup membership, and never receives their discrete-log labels. Eight target points were frozen from the separate SHA-256 domain `ECC2K53-COMPACT-POINT-BATCH-20260924-v1/`; the validator labels are in the manifest, which is not passed to the Rust process. The final source extracted all eight in a second cold process. Python independently lifted every witness, computed the scalar from the previously solved orbit logs, verified `[scalar]G = Q`, and only then compared it with the validator label: **8/8 recovered**. Off-curve `[0,0]`, order-two `[0,1]`, and a point file supplied without compact extraction were all rejected. The point process took **12.394 seconds wall**, peaked at **646,250,496 bytes RSS**, and spent 8.257 seconds in extraction queries. This is a separate cold process, so it rebuilds the index; summing its wall with training wall is an inclusive two-process synthetic completion, not a warmed-throughput or matched-rho comparison.

The result moves the compact producer from isolated relations to a full-rank base and point-only n=53 recovery. It does **not** establish an advantage over optimized rho. The repository's earlier [batched-rho study](../autolab_batched_rho_n53_20260922/RESULT.md) found that a different, faster but much larger IC implementation lost to shared-work Kuhn–Struik rho across its tested batch sizes; those timings cannot be transplanted to this source, host and target stream. This compact implementation's per-point extraction is also much slower than that study's warm IC queries. The next decision gate is a matched target-stream, same-host, cold full-cost comparison against signed-Frobenius batched rho, plus n=37/n=41 repetitions and an explicit n=131 transfer model. A relation-stage or single-solver speedup cannot close that gate.

Reproduce the frozen receipt from a release build with:

```sh
cargo build --release --example koblitz_s5_sat_instance --offline
python3 research/sat_factor_base_review_20260908/autolab_orbit_extract_20260924/cold_batch_rank.py --out /tmp/cold-rank-new --targets 512
python3 research/sat_factor_base_review_20260908/autolab_orbit_extract_20260924/run_point_batch.py --training /tmp/cold-rank-new --out /tmp/point-batch-new --targets 8
python3 research/sat_factor_base_review_20260908/autolab_orbit_extract_20260924/recover_point_batch.py --training /tmp/cold-rank-new --point-batch /tmp/point-batch-new
```

Fresh timings will vary. To independently replay the committed training relation file without rerunning the producer, use `cold_batch_rank.py --replay-only --out research/sat_factor_base_review_20260908/autolab_orbit_extract_20260924/cold_rank_20260924_codex --targets 512`, then run `recover_point_batch.py` against the committed `point_recovery_20260924_codex` directory. The manifests pin source/executable/input hashes and stopping rules; the raw JSONL and rejection stderr remain alongside the validation receipts. The training source SHA is the #714/#720 producer, while the final point source SHA is the follow-up above.
