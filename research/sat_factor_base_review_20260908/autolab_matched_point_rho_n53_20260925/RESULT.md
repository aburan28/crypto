# Cold point-only rho on the compact n=53 target stream

The fixed eight public subgroup points from [the compact full-rank/point-recovery experiment](../autolab_orbit_extract_20260924/COLD_BATCH_AND_POINT_RECOVERY_20260924.md) were solved by a cold, signed-Frobenius Kuhn–Struik batched rho process. The rho child read only `[x,y]` coordinates, never target scalar labels. An independently coded Python binary-field and group implementation recomputed `[d]G` for every rho output and compared it with the withheld validator labels. Three cold seeds recovered all eight points, and each also solved the exact first-point prefix. The final compact producer recovered the same first point in a separately measured cold process; its witness and factor-base logarithms passed the upstream independent replay. On these fixed n=53 inputs, the fully charged compact method was slower in every measured rho block.

The [rho protocol](protocol.json) was locally committed as `36ec7aa8` before the rho runs; the GitHub PR commit uploaded those frozen bytes later. It fixed the byte-exact eight-point stream (SHA-256 `41d23eda5bcceba8270bdf0fcc742a570006ff647ddaf8b4735140dcf43fffe8`), prefixes 1 and 8, seeds 531310–531312, 32 jumps, distinguished-point density 1/16, signed Frobenius plus negation (106 automorphisms), no precomputed G-only walks, and one fresh table per process. Rho source SHA-256 is `fedacb54e441979c8c32860e7b5639e43799234741d49677010164564536d2c8`; each [run manifest](runs) records the executable hash. The [one-point IC addendum](ic_single_addendum_protocol.json) was separately committed locally as `d7b4ec64` before that run, **after** the rho results were seen. It fixed the first point, final upstream source/executable hashes, one cold process, stopping and cost rules. No seeds or failures were replaced.

The compact-IC training process took 158.127 s and reached all 220 columns at relation 461; it continued to the frozen 512-relation stopping rule, so the table charges 51 additional held-out relations. Its **separate cold** first-point process took 1.789 s, and its separate eight-point process took 12.394 s. Both completions charge their own target-process setup; only the measured positive process is counted, while three negative-control processes are validation. The final point-producer source SHA-256 is `b88ab958f3044211ddcb230863a4175916000c2c15307a7572dec40a4e55204d`, executable SHA-256 is `01ab8d0b09f72908281124ae3ae4fdde88f538abdc1fc2c574309dfc1777990c`, and eight-point stdout SHA-256 is `7d4f46316b6a0d718b329dbb1c734edc2baf4726621842d18b2fa4c6a3b45303`. The rho processes include 32-jump construction, point parsing and subgroup checks, all walks and distinguished-point table activity, and candidate scalar verification. Eight-point rho user-plus-system CPU times were 2.485, 3.162, and 3.478 s; group additions were 1,148,987, 1,400,555, and 1,492,522; peak RSS was 18.0–19.9 MB.

The host was heavily shared: five-minute load averages at rho launch were roughly 32–50, and the 19.256 s rho wall used only 2.485 s child CPU. The compact-IC archive and one-point addendum were measured on the same host, but not in contemporaneous paired blocks. Wall dispersion is therefore reported verbatim, with CPU and operation counts as context. This is a no-crossover for these exact cold, fully charged n=53 completions. It is not an optimized asymptotic rho result, an n=131 transfer, or a general batch-size crossover. A future paired full-rank run should stop at first full rank and measure n=37/n=41/n=53 target streams under balanced load.

The original rho protocol incorrectly proposed comparing its L=1 rho prefix against the eight-point IC numerator. That comparison was rejected. The separately preregistered **post-panel** IC first-point run supplies the L=1 numerator in the table. Exact n=53 rho negative controls rejected off-curve `[0,0]`, order-two `[0,1]`, and out-of-range coordinates. A preliminary n=7 scalar-derived smoke at seed 42 hit the producer step cap; it was unrelated to the n=53 panel and is preserved in [its stderr](smoke_n7_failure.stderr.txt).

To replay the committed evidence from the repository root, run `python3 research/sat_factor_base_review_20260908/autolab_matched_point_rho_n53_20260925/replay_ic_single.py` and then `python3 research/sat_factor_base_review_20260908/autolab_matched_point_rho_n53_20260925/analyze.py`. The first script rehydrates the frozen base header from the already committed gzip, replays the one-point IC witness and confirms its validation receipt byte-for-byte. The second independently checks all rho scalars, source/input hashes, full-cost charges, and decisions. To take new rho measurements, build with `cargo build --release --example koblitz_rho_batch_ks` and invoke [run_rho_points.py](run_rho_points.py) once per protocol `run_order` entry using a fresh output directory. The runner refuses a source or target hash mismatch and preserves incomplete or timed-out runs.
