# Matrix-F5 byte-subset output unpack: frozen experiment

## Hypothesis and baseline

The exact one-thread n24 degree-4 F5 call returns 6,924 rows with 13,734,979 monomial terms. The current direct scalar unpack takes about 45–55 ms by visiting every set bit and indexing the monomial column list for each term. Precompute, once per call, the ordered monomial sequence for each 8-column subset. Each output row then scans its packed bytes and copies the corresponding contiguous slices into its exact `Vec<F2BoolPoly>` rows. This could trade about 14 MiB of per-call lookup data and construction time for fewer per-term random lookups; both costs belong inside the complete-call interval. Preserve output order and every matrix/elimination operation exactly. The option `KIC_F5_UNPACK_BYTE_TABLE=1` selects the candidate only for the direct scalar unpack route with at least 4,096 columns; `=0` retains the reference. The table must have a 16 MiB cap and otherwise fall back.

The frozen pre-candidate source is commit `043e4965801488d530d3ba9fd7e29b87276a5eb6`, dependent on branchless-strip PR #998. SHA-256: `matrix_f5_f2.rs` `bf35680f431ab7ac13a7615d334ec9b060217b84bdde36f03ce00319491d42da`, `gf2_elim.rs` `6fd3f10ef8e681490784c624e703eeb8fa887c5817ec9bdf34844e3f943c7f5c`, `koblitz_groebner.rs` `cc50fa7dee14d6c606883713fe842139a1d25f636c57be99817ca63607c2b816`, benchmark `f4_f2_bench.rs` `d40f9f0c76e5c56c9f4a52596b9edef41f321aa3d70cfb023c4ba21fdde70336`, isolation wrapper `ff59e53fd5566078ad493c8be0d06168699c4fd194bc881d99df19fa20e007ef`. The qualified unchanged-source baseline from PR #1001 has binary SHA-256 `604a81550ed7fc1caa232fffa2aee5850658a2092e6f3bd5dad8d26c43abd293`, seven exact cases and a 90.463 ms primary call on its Xeon runner. It is a reproducibility baseline, never a cross-host denominator. Before candidate timing, preserve an unmodified release binary/manifest built from the frozen source and record its hash, host, compiler, flags and exact outputs. Candidate ratios use one release binary with explicit `=0/1` processes on the same runner.

## Workload, isolation and decision

Use all seven F5 cases of `examples/f4_f2_bench.rs`, primary `f5_n24_m24_d4`, four seed XORs `0`, `badc0de1`, `5eed2026`, `f5c02a28`, one Rayon thread and a separate two-thread control. Hold selective echelon output, fused row counting, direct packed rows, branchless AVX2 strip clearing, direct scalar unpack, AVX2 row XOR and table reuse fixed across modes. Disable deferred above, word batching, AVX-512 unpack and experimental table building. Per seed and thread count: one warmup per arm, five A/A reference pairs and five alternating A/B pairs. Each process runs all seven cases. Preserve every call, failure, timeout, source/binary hash, CPU/affinity, all exact output/count fields, and exclusive criterion/build/elimination/unpack/full-call timings. Raw and canonical fingerprints, rank, terms, columns, built/pruned counts, criterion and reduction word operations must match on all cases. The primary candidate route must be selected only for mode 1; smaller cases below the threshold must use the reference route.

Build/tests use `tools/isolated_bench.py busy` under a shared lock in `RUNNER_TEMP`. Each timed harness uses a noninteractive privileged `reserve`, reserves all SMT siblings and leaves at least one CPU free. Pass the runner's Rustup home/PATH to the privileged harness. Require a successful 10-second preflight with default maximum other-CPU 0.10 and PSI 5.0, zero eligible user threads left on reserved CPUs, and zero contended samples at 0.25-second sampling. Preserve all refusals and contended receipts; they are exactness/provisional diagnostics only. The process-snapshot monitor correction in frozen source is part of the isolation wrapper, not the solver candidate.

The candidate advances only if every call is exact, the one-thread primary paired complete-call median is at least 1.10 and its exact 3,125-resample bootstrap 95% lower bound exceeds 1.05, no seed or smaller case has a complete-call median regression outside its A/A range, the two-thread control has no such regression, and the table remains within 16 MiB. This higher incremental gate prices its extra memory. If it fails, preserve the measured patch and all receipts, remove the runtime candidate and one-off workflow, and report the negative result. If it passes, run a separately frozen default-on confirmation before merge. The user's further 2× goal requires a measured one-thread full-call ratio and lower bound over 2.0 relative to the declared exact-output reference; this experiment alone is not expected to clear that gate. All comparisons here are solver-stage diagnostics, not one-target IC online DLP or rho speedups.
