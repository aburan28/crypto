# F5 fused Macaulay row count and materialization

## Hypothesis and reference

Matrix F5 currently traverses and sorts every Macaulay product once to count the unpruned F4 rows, then traverses and sorts the surviving products again to materialize F5 rows. The candidate shares one traversal: it still constructs every product to count nonempty F4 rows exactly, and saves only rows that pass the unchanged F5 criterion. This should lower the F5 build phase without changing its rows, order, matrix, RREF output, or counters. The previously frozen `koblitz_groebner.rs` source can now evolve because PR #801 merged historical source snapshots for its replay.

The unmodified baseline is `7b77244d1ddc60b32b34e3cd010722b7ae45197c`. Its `koblitz_groebner.rs`, `matrix_f5_f2.rs`, and benchmark source SHA-256 digests are `1590fd2991759b3f0d819705e54fa1d1107cfb6ba676c30a0703cfe8881a63c0`, `592761e4da6a385fa0145b8a548d86ca7b2930d0322398f1dcae07cc96dbeccb`, and `812fdc75bd89c7ac7944a2631158dc02bf1861fed25aa72fd629774daeb6f37a`. Build and retain its release example binary beside the candidate binary. Use identical Rust flags and a pinned Linux runner; record binary digests, Rust version, CPU model/features, memory, load and core affinity. In both arms use RREF output, one F5 repetition per process, `KIC_GF2_DEFER_ABOVE=0`, and `KIC_GF2_WORD_BATCH=0`. The candidate selects its fused row builder with `KIC_F5_FUSED_BUILD=1`; the baseline has no such flag.

## Frozen paired workload

Run the seven standard matrix-F5 cases in `examples/f4_f2_bench.rs`, primary `f5_n24_m24_d4`. Freeze seed XOR zero and holdouts `badc0de1`, `5eed2026`, and a fresh `f5a28c01`. Pin one Linux CPU and set `RAYON_NUM_THREADS=1`. Warm each arm once per workload; collect five A/A baseline pairs and five alternating-order A/B pairs per workload. Save every process status, complete output, phase timing and counted operation in a raw receipt before the next call. Pair only within a workload and runner; report exact five-pair bootstrap 95% intervals and each case's A/A range. `f5_build_ms` covers criterion-independent F4 counting, F5 row construction, column construction and packing. `wall_ms` covers the complete matrix-F5 call but excludes process launch and fixture construction. If the one-thread gates pass, repeat the paired design on four pinned CPUs.

Require exact raw row fingerprints, canonical row-space fingerprints, rank, rows pruned, criterion and elimination word-operation counts for every case and workload. Unit tests must compare the original and fused row list and full row count on randomized and cancellation-heavy polynomials, including cap behavior. The first candidate passes its stage gate only if the frozen primary build median baseline/candidate ratio reaches 1.25 with its 95% lower bound above one, the complete-call ratio and lower bound exceed one, both original holdouts and the new holdout show a build gain outside A/A noise, and no smaller complete-call median falls below its own A/A range. If any gate fails, retain the original builder and preserve the result without timing-driven repeats.

The user's 2× goal applies to a **complete F5 call against the current RREF default**, not to a phase or to multiplication of independent ratios. This fused builder is one bounded candidate. If it passes, measure a separate, prospectively specified combination with the already explicit selective-echelon form; changing the output basis requires canonical row-space comparison and must not be called an exact-output speedup. Neither stage result is a one-target IC or DLP speedup claim.
