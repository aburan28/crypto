# hdl/ecc — FPGA engine for secp256k1 point arithmetic

A pipelined modular multiplier and an elliptic-curve point adder built
around it, in portable VHDL-2008. Together they are the datapath of a
Pollard-rho ECDLP engine; the same algorithm the CUDA kernels in
`gpu/ecc/` implement, so the two can be compared directly. That comparison
is [`docs/ecc_fpga_cost_model.md`](../../docs/ecc_fpga_cost_model.md).

Reference part is the AMD Virtex UltraScale+ VU47P (AWS `f2.6xlarge`), the
same one `hdl/sha1/` targets, but there are no vendor primitives here — it
is plain `ieee.numeric_std`, simulates under GHDL and reads into any
synthesis flow.

## Files

| File | What it is |
|---|---|
| `fp_pkg.vhd` | The prime, the reduction constants, modular add/sub, pipeline depths |
| `fp_mul_secp256k1.vhd` | 256-bit modular multiplier, II = 1, latency 12 |
| `ec_add_pipe.vhd` | Affine point addition scheduled around one shared multiplier |
| `fp_mul_tb.vhd` | Self-checking testbench, 256 vectors back-to-back |
| `ec_add_tb.vhd` | Self-checking testbench, 64 point additions |
| `vectors_secp256k1.txt` | Generated by `gpu/ecc/ecref.py` — the same oracle the CUDA tests use |

## Run

```bash
make            # analyse, elaborate and run both testbenches
make vectors    # regenerate the vector file from the Python reference
```

Needs GHDL (`apt install ghdl`). Current output:

```

=== ec_add_tb ===
```

The vectors include the cases that break careless reduction logic: zero,
p−1 squared, 2^255 squared, and 1·(p−1).

## The multiplier

Eight operand-scanning rows followed by three reduction folds.

Row *i* forms `t = acc + a(31:0)*b`, emits `t(31:0)` as the next product
limb, and passes `t >> 32` to row *i+1* with the multiplier operand shifted
down 32 bits. Each row is one 32 × 256 multiply — eight 32×32 products,
about 32 DSP48E2 slices — and one 296-bit add. Eight rows retire one full
256×256 product per clock.

The emitted limbs are collected in a shift register, entering at the top and
walking down, so after eight rows the low half of the product is in natural
order. That keeps every slice index locally static, which matters for both
simulation and synthesis.

Reduction uses 2^256 = 2^32 + 977 (mod p), the same three folds as
`Fp::secp_reduce` in `gpu/ecc/fp256.cuh`:

```
U = Lo    + Hi*977   + (Hi   << 32)     < 2^289
V = U_lo  + U_hi*977 + (U_hi << 32)     < 2^256 + 2^66
R = V_lo  + V_hi*(2^32 + 977)           < 2^256
```

then one conditional subtraction of p. The third fold cannot carry out
again because `V_hi = 1` forces `V_lo < 2^66`.

The `tag` port travels with the operands and the datapath never looks at
it. That is what lets one multiplier serve many independent walks at II = 1
with no stall logic anywhere.

## The point adder

```
lam = (y2 - y1) * inv          inv = 1/(x2 - x1), supplied by the caller
x3  = lam^2 - x1 - x2
y3  = lam*(x1 - x3) - y1
```

Three multiplies, each depending on the last. A single point addition
therefore cannot fill a 12-stage pipeline — it would idle 11 cycles out of
12. `ec_add_pipe` keeps many *independent* additions in flight, cycling
between the three phases and issuing one multiply every clock. Each request
gets a slot from a rotating pool of 16; the slot rides through the
multiplier in its tag field, so results route back to their context with no
matching logic and no back-pressure. A slot is reused after 48 clocks, well
past the ~38 an addition lives.

Measured result: **2.98 clocks per point addition**, i.e. the multiplier
runs saturated, and one point addition costs exactly three modular
multiplies with no pipeline tax.

The inverse comes from outside on purpose. In the full rho engine one
inversion is shared across a whole batch of walks by Montgomery's trick,
which is what makes affine coordinates cheaper than projective ones here —
the same reason the CUDA kernels batch.

## Running it on real hardware

[`aws/`](./aws/) has scripts to synthesise this on an AWS build instance and
bring back utilisation and timing, which is what turns the estimates in the
cost model into measurements. They have not been run — there was no AWS CLI
or Vivado in the environment where they were written — and they synthesise
only; producing a loadable FPGA image needs an AWS shell wrapper this
datapath does not have. See [`aws/README.md`](./aws/README.md).

## What is not here

- **The rho sequencer**: walk state storage, the r-adding jump table in
  BRAM, distinguished-point detection and the output FIFO. The datapath is
  the part with the interesting engineering; the sequencer around it is
  bookkeeping, and the CUDA implementation in `gpu/ecc/rho.cuh` defines the
  semantics it would have to follow.
- **The inverter**: Fermat inversion reusing this multiplier, 270 issue
  slots, amortised over the batch.
- **Karatsuba** on the 32×32 products: 3 DSPs instead of 4, a 25% DSP
  saving for some LUTs.
- **A deeper row adder.** This is the important one. The critical path is
  the 296-bit adder in each row, roughly 37 CARRY8 levels, which caps the
  design near 300 MHz — well short of what the DSP48E2 can do. Splitting
  each row adder in two (16 row stages, latency 20) should reach 500 MHz
  and costs nothing in throughput, since II stays 1 and the engine already
  tolerates latency by interleaving more walks.
