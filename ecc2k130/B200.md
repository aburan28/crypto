# B200 (Modal) — can a datacenter Blackwell beat the RTX PRO 6000?

Every audited walk rate in this tree is for the **RTX PRO 6000** Blackwell
workstation part, `sm_120`, 188 SMs: 15.115792 B/s on the matched TOP_CLMAD
control ([benchmarks/top-clmad](benchmarks/top-clmad/summary.json)) and
~14.1 B/s collecting. Modal also rents the **B200**, `sm_100`, a datacenter
Blackwell GPU. This note is that part's rate table. It does not change the
campaign default.

The walk is integer/carryless-bound, not tensor-core-bound
([THROUGHPUT-30B.md](THROUGHPUT-30B.md)). LLM B200-vs-6000 numbers do not
transfer. The B200 has **fewer SMs** (published 148 vs 188) and typically a
lower sustained clock than the 6000's ~2.4 GHz, so the interesting question
is whether per-SM issue on `sm_100` makes up the gap.

## 1. How to measure

```bash
make bench-b200-modal            # Modal B200, shipping CLMAD=1, automatic workers
B200_CLMAD=0 make bench-b200-modal   # software-product before-arm
make validate-b200-modal         # planted logs on the B200 itself
```

Same geometry as Ada ([ADA-L4-L40S.md](ADA-L4-L40S.md)): batch 16, 256-thread
blocks, two resident blocks, compact storage, shared masks, CUDA 13.3.1.
Workers stay **automatic**. The 6000 preset's 385,024 is four waves on a
188-SM part and has no claim on a 148-SM one; `autoThreads` sizes the grid
from `multiProcessorCount`.

`PACKED_CLMAD` is on for the shipping arm: `sm_100 >= 800`, so the device
path emits `clmad` ([include/packed131.h](include/packed131.h)). The
software arm is the superseded before-mark, measured on a separate Modal
allocation the same way the Ada receipts were.

Writes under [benchmarks/b200](benchmarks/b200/). The page cites those
files and does not recompute.

## 2. Boundaries, written before the run

Unit: billions of completed scalar updates per second. Class: engineering
(same walk, 5.3125 products/update).

| | value | kind |
|---|---|---|
| Floor (one-add walk on a 188-SM 6000) | ≈ 23–25 B/s | 6000 number; a 148-SM part cannot be asked to cross it |
| Reference | 15.115792 B/s on RTX PRO 6000 | [top-clmad](benchmarks/top-clmad/summary.json) |
| Prior, SM-count only | **11.90 B/s** | 15.115792 × 148/188, equal clock and per-SM issue |
| Prior, SM × H100-like clock | **~9.0 B/s** | extra × (1.83 / 2.42); clock is unmeasured here |
| Modal list, 6000 | $3.03 / h | $0.000842 / s |
| Modal list, B200 | $6.25 / h | $0.001736 / s |
| B200 it/$ break-even vs 6000 collecting 14.1 B/s | **29.1 B/s** | 14.1 × 6.25 / 3.03 |

The 29.1 B/s break-even sits above the 6000's own integer-pipe ceiling.
A B200 that merely matches the 6000 still loses on Modal iterations per
dollar. The rate still has to be measured: a surprise per-SM win would
show up as beating the 11.90 prior, and would still be engineering unless
it also beat the 6000's 15.116.

Success is a verified median on a GPU whose name contains **B200**, compute
capability **10.0**, identity matching the requested build (including
`packed native carryless multiply: 1` on the shipping arm), automatic
workers, three valid `--bench` repeats. Inadmissible: filing an H100 / H200
/ B300 / RTX PRO 6000 number here, using 385,024 workers, skipping
validate, quoting tensor-core marketing, or promoting the campaign onto
B200 from `--bench` without a collecting rate.

Falsify the "B200 is faster" claim if the shipping-arm median is below
the 6000's 15.115792 B/s. Falsify the SM-count prior if the measured
rate is far from 11.90 after recording the actual SM count and clock.
