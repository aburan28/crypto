E3  float-precision audit of shipped gauss_reduce_2d()
==========================================================================
  The shipped routine computes  q = round(<u,v> / |v|^2)  with float
  division of Python ints.  Both operands grow like (n*S_K1)^2 ~ n^4.

 bits  n^4 bits  trials  float==exact  overflow/NaN  max rel err
   16        64       8        8/8                0     1.15e-16
   24        96       8        8/8                0     1.31e-16
   32       128       8        8/8                0     1.36e-16
   64       256       8        8/8                0     1.26e-16
  128       512       8        8/8                0     2.29e-16
  192       768       8        8/8                0     1.35e-16
  256      1024       8        8/8                0     2.70e-16
  384      1536       8        8/8                0     1.34e-16
  521      2084       8        0/8                8     0.00e+00

  Diagnosis of the failure mode:
    |u|^2 has 1565 bits (float64 overflows above 1024)
    int/int true division  <u,v>/|v|^2     -> 1.0
    math.sqrt(|u|^2)                       -> OverflowError: int too large to convert to float
    => Python's int/int division is correctly rounded and does NOT
       overflow; the failure is the final math.sqrt() on a >1024-bit int.
    RELEVANCE TO PRIORITY THREAD 1 (P-521 LLL NaN): the same pattern --
    math.sqrt / float() applied to an exact big int -- is a candidate
    cause of NaN at 521 bits that is NOT a Gram-Schmidt precision problem
    and needs no bigfloat library to fix (use math.isqrt, or rescale by
    bit_length, instead).  Worth checking before adding a rug dependency.
