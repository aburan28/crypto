# Prepared S3 relation space for one-target recovery

The prepared implementation completes a 244-column relation basis and certifies
its factor-base logarithms **before reading the public target point**. Online
work then consists of subgroup validation, one four-point S3 decomposition,
linear recovery, and scalar replay. All 24 frozen N41/N53 public points were
recovered by both implementations in the local paired panel. Independent Sage
arithmetic recovered every scalar again and checked 1,344 distinct relation
witnesses from the two curves.

## Local paired result

The panel uses one fresh process per candidate and point, alternating arm and
curve order over 12 frozen points per curve. Each run uses relation seed
`20260928`, 14 relation/index workers, the same public point, a 180-second cap,
and source snapshot `833ef86191947ba8e4def56a78ee6c51a4ea0ff2` plus the
prepared example's SHA-256 in the environment receipt. All 48 runs completed,
verified the scalar, found a target relation, and passed the exclusive-phase
sum check. The prepared arm reached rank 244 before target input on every run.

| Field | Reference online median | Prepared online median | Geometric mean of paired online ratios | Smallest paired online ratio | Reference / prepared cold median |
| --- | ---: | ---: | ---: | ---: | ---: |
| N41 | 339.747 ms | 0.432 ms | 416.04× | 6.65× | 1447.094 / 1291.240 ms |
| N53 | 8464.510 ms | 92.768 ms | 101.09× | 5.26× | 9908.265 / 30327.232 ms |

These are **exploratory local wall measurements**. The shared ARM64 Mac had
concurrent Rust and Sage work, no exclusive CPU partition, no fixed frequency,
and no run-level PSI/IRQ/steal receipt. In particular, some submillisecond
prepared N41 online intervals were interrupted by much longer scheduler
delays. The archived ledger retains those outliers. `controlled_speedup` is
`null`; the online ratios are not a promoted CPU performance claim.

The deterministic S3 root-call boundary confirms the mechanism independent of
the host clock. Across these points, the smallest reference/prepared ratio of
**target-dependent online S3 root calls** is 89.29× for N41 and 51.13× for
N53. The target decomposition itself makes the same S3 calls in both arms.
The prepared arm moves rank collection into reusable preparation and performs
more relation work there: 294 rather than 252 attempts on N41, and 560 rather
than 238 on N53. The full preparation and cold costs are present in every
measurement row and in [`analysis.json`](local/analysis.json).

The online timer starts at target validation after the prepared relation basis
and logs are ready. It stops after scalar replay. Target input loading and
known-scalar fixture generation lie outside the online timer. The five
exclusive costs are `target_query`, `target_pdp_charged`,
`target_relation_check`, `target_descent`, and `target_recovery_check`;
their sum is checked against `target_online_after_reusable_setup` in every
run. The frozen reference charges target-span relation collection to the
online interval because its stop rule depends on that target. The prepared
variant's full-rank stop rule and queries are target independent.

## Modal panel ready for approval

[`modal_prepared_panel.py`](modal_prepared_panel.py) is prepared to build both
examples on a 16-CPU Modal VM, run a one-point smoke and a 12-point ABBA/BAAB
panel, retain all raw failures, collect a prepared-arm A/A control, record
guest affinity/NUMA/cgroup/PSI/interrupt/steal data, and run a separate
whole-process `perf stat` diagnostic. The image upload selects `Cargo.toml`,
`Cargo.lock`, `src/`, `docs/ic/`, `docs/ecbench/`, `docs/curves/`, the two
frozen S3 examples, the new prepared example, and the pilot/warmup fixtures:
1,246 files totaling 52,238,498 bytes, plus the runner code. A scan of that
upload set found no private-key or API-token patterns. The repository is
public; the newly written prepared source is not yet published.

Automatic approval review rejected the Modal upload twice because uploading
the selected source, build metadata, and fixtures to a third-party service
needs explicit authorization. No Modal job was started. With authorization,
run the smoke first and the full panel only after its correctness gates pass.
The Modal VM can improve exploratory CPU diagnostics but cannot itself prove
host-wide exclusive CPU, IRQ, frequency, and memory-node control. A strict
isolated-host receipt and a fresh confirmatory target panel remain the gates
for a controlled CPU wall-time claim.
