# Immediate S3 target lookup with projective target checks

The new [direct-lookup source snapshot](../../examples/s3_partial_prepared_fullrank_projective_directlookup_targetspan.rs) checks each S3 partner against the root table as soon as its roots are available. It retains the eight-state shared inversion, the target search order, projective subgroup validation and scalar replay, and the opt-in ARM64 PMULL fold. A verified relation can now stop the remaining roots in its batch. The release build is bound in [build_receipt.json](local/build_receipt.json).

On public N41 target T220 with a **244-column diagnostic index**, both the direct-lookup and prefetch binaries recovered scalar `254961180376` using 20,008 actual subgroup-usable factor-base points and full prepared rank 244. Checked Sage independently replayed both scalars on the frozen public point. The direct path made **1,170 S3 calls** versus **1,184** for prefetch. This single pair had online intervals of 0.719 ms and 0.403 ms, and charged target-PDP intervals of 0.654 ms and 0.385 ms, respectively. These timing values are diagnostics from the contended Mac, not an aggregate comparison. See the [Sage receipt](local/smoke_replay.json) and the [direct](local/direct_c244_T220.json) and [prefetch](local/prefetch_c244_T220.json) native reports.

The first **C1200** T220 smoke reached its 180-second process cap with an empty report. The exact stopping phase is unknown. Its [failure receipt](local/c1200_timeout.json) retains the source and binary hashes, public-point hash, command shape, and cap. This host's earlier C1200 setup times varied sharply, and workspace free space fell from roughly 47 GiB to 10 GiB while the release build and smoke were running. The current host cannot support a reliable C1200 timing conclusion from this attempt.

The [preparer](prepare.py), [runner](run.py), [analyzer](analyze.py), and [checked Sage replay](replay_sage.py) are drafted for a 12-point, alternating-order C1200 screen against the existing prefetch/PMULL candidate. **No C1200 screen has been frozen or launched.** Before that screen, run a fresh preparation pilot on the chosen host, choose a process cap and resource envelope from its observed setup, and then freeze the candidate manifest, binary hashes, run order, and one-target workloads. If that screen improves charged PDP and online time, use previously unused points for a fixed-size confirmation. A controlled CPU wall-time result also requires the repository's host-exclusive isolation receipt and noise gates.
